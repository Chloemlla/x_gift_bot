# Explicit public payment-link regeneration

A public POST to `/api/manual-link` is a generation request. A distinct browser-owned `request_id` queues creation of a **new** X checkout session, including when an earlier session is open, stale, expired, has a different plan, or has an unknown payment outcome. Payment status reads and queue polling never generate sessions. Creation calls the existing X `useOneTimePurchaseGiftMutation` only; it never tokenizes a card, confirms a PaymentIntent, or replays a payment submission.

The frontend uses a random request ID, retains it through retry/reload, and changes it when the user explicitly selects regeneration. Concurrent/repeated IDs share one ticket and a persisted generation reservation. A retry with changed parameters is rejected. Legacy tickets derive a stable generation ID from their unchanged ticket ID. An ambiguous creation attempt is not replayed for the same ID; a separate explicit generation may proceed, retaining the earlier reservation/audit. Failed live reads remain unknown, not proof of nonpayment.

All replaced orders remain in the encrypted public order's `history`, with their original session, product, amount, identity, payment status, and verification evidence. Existing X creation audits and guarded Stripe snapshots remain stored separately. Regeneration and browser status lookup inspect retained sessions using original prices. A verified payment on any retained session prevents further generation. An older paid session is updated as that session; it never marks a newer session paid. Confirmed success cannot be downgraded by a stale read. Private/redemption orders remain excluded from the public path, and only the owning browser may regenerate an existing public order.

The three-minute timer is a **local queue/payment window**, not evidence that Stripe has invalidated a link. Stripe documents merchant-side expiration for open sessions at [Expire a Checkout Session](https://docs.stripe.com/api/checkout/sessions/expire). This integration has an X checkout-creation contract and a Stripe publishable key, not a supported merchant secret-key expiration contract. No expiration/cancellation API was invented or invoked. Previously delivered URLs may remain payable, and payments may finish between status checks and creation. Two browser payments on two sessions remain possible. Warnings advise checking prior payments and avoiding payment on multiple links. This implementation does **not** guarantee duplicate-payment prevention or entitlement delivery. Historical reconciliation is read-only and occurs on generation/status lookup; it is not a payment replay or an exhaustive autonomous settlement sweep.

Upstream rate limits, catalog/recipient validation, private-order isolation, authenticated browser ownership, and confirmed-completed protection still apply. The 15-second upstream creation pacing and queue scheduling remain. An elapsed foreign public queue window can yield to an explicit link-only request even when its payment is unknown, without declaring it unpaid; automatic payment paths retain their existing uncertainty protection. an old session's local age, changed plan, or unknown outcome does not by itself deny an explicit regeneration. If X returns the same retained session ID, the application refuses to label it fresh and preserves the attempt as uncertain.

Deployment replaces code artifacts only. Existing runtime databases, vault credentials, encrypted histories, queues, and ticket ordering are retained under the existing checkout/site/legacy queue locks. A code rollback restores binaries and revision only, never databases over live transactions.
